# 検証と完了判定 v4

## 設計キットの試験と、アプリ本体の試験を分ける
キット：JSONの参照整合、全要件のタスク対応、依存循環、UI並行性、SVGの表示・操作、テンプレートと正本の一致、GitHubツールのdry-run。
アプリ：本人の実Claude、Google等の実データ、旅程生成・編集・保存、複数ユーザー認可、SNS、PDF、ICS、スマホ、再起動とバックアップを実際に検証する。このキット生成だけではアプリ試験を実施したことにならない。

## 重要な受入シナリオ
1. 新規生成：入力→202 jobId→実Claude→候補の共通DB保存→候補表示→採用→別端末から旅程読出し。
2. 版競合：2端末がrevision=3を読出し、一方が4へ更新。もう一方のPATCH/候補採用は409。既存変更を消さない。
3. 再計画：訪問済み・固定予約を維持し現在地から残りだけ変更。不明の運賃をゼロにしない。
4. SNS：Aが非公開旅程からgroup投稿。A/Bは見えCは404。Bを除外すると同じURLで404。private変更でも拒否。
5. コピー：Bが閲覧可能なsnapshotから新旅程を作る。owner=B、revision=1、元秘密情報なし、新日付は要再検証。Aの元旅程は変化しない。
6. CLI失敗：未認証、上限、timeout、invalid JSON、cancelでfailed等を正しく返す。公開入口からCLIは起動できない。
7. 永続化：サーバー再起動後に旅程・投稿・権限が保持。バックアップを別DBへ復元し内容確認。元DBを壊して試さない。
8. UI：fixtureから初期レビューを行い、実接続後も同じ契約で正常/失敗/待機を表示。
9. 外部出力：時差を保持してICSを読み戻す。PDFには許諾のある素材だけ。未実装の自動外部登録はできると表示しない。

## 証拠
各タスクに実行環境、commit、コマンド、終了コード、件数、fixture/live、期待結果と実結果、担当、独立review、UI人間承認を添付。全機能は対象に残し未達を明示。2日で全機能完成する保証や、全世界の正確な時刻表を取得できる保証はしない。
