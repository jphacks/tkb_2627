# U02 UIレビュー記録 v1（対象: U01）

- 対象: U01「最初のクリック可能なUI」（#9, PR #82, merge `946d046`）
- 画面: `npm run dev -w @tkb/web` → http://127.0.0.1:5173/src/screens/preview.html（モックのデータ）
- 日付: 2026-10-24
- レビュー: M2 担当者（@murataka-csl）が画面を操作して指摘した。記録は M2 の Claude Code が整理した
- データ: すべてモック／fixture。実 API・実 AI・実際の地図では確認していない

## 判断の表し方
- **採用**: 対応するタスクで実装する。契約は変えない
- **要調整**: 契約・計画ロジック・費用などで、ほかの担当の判断や作業が要る。UI 側で対応する方針でも、確定はその判断のあとにする
- **M1 通知（契約）**: 受渡し型（契約）を変える可能性があるもの。U02 の受入条件により、M1 にはこれだけを通知する
- **調整（契約は変えない）**: 担当や本人の判断が要るが、受渡し型は変えないもの。対応するタスクの Issue で確認する

## 指摘と判断

### R1. 「上へ・下へ」をやめ、ドラッグ＆ドロップで並べ替える
- 画面: 旅程の詳細と編集
- 指摘: 予定ごとの「上へ」「下へ」ボタンをなくし、ドラッグ＆ドロップで直感的に入れ替えたい
- 判断: 採用
- 対応: U06（#34）旅程編集。並べ替えは K10 の `move` で表せる
- 注意: キーボードだけで操作する人のための代わりの手段（例: 選んで矢印キー）を残す。タッチ端末でのドラッグも U06 で確認する。ドラッグ中の版競合（409）は今と同じく上書きしない
- M1 通知: 不要

### R2. 予定をタップすると、その予定の詳しい内容が開く
- 画面: 旅程の詳細
- 指摘: 予定をクリック／タップすると、その中の具体的な内容が表示されるようにしたい（手描き案 2: 「9:30〜50 ○○」の行を開くと、9:30 B1、9:40 B2、9:50 B3 のような細かい行が出る）
- 判断: 表示は採用。中身のデータは要調整
- 対応: U04（#32）地図と旅程の同期画面
- 要調整:
  - 移動の細目（乗換の各区間）は、今の `TravelLeg`（路線・乗り場・乗換・発着時刻）を続けて並べれば表せる可能性が高い。データは D04（#14, M3）の経路取得に依存する
  - 施設の中での回り方などの細目は、今の `ItineraryItem` では表せない。表すには契約の追加が要る。データは D03（#13, M3）の取得値に依存する
  - 細目の取得元がない場合は、AI に作らせず「未取得」として表示する（CLAUDE.md §2: 不明な値を生成で補わない）
- M1 通知（契約）: 条件付きで要。施設内の細目を `ItineraryItem` に持たせる必要があると M2・M3 で確かめた場合に通知する

### R3. 表形式で表示し、1つの枠に地点は1つだけ。滞在時間を「9:00〜10:00」で示す
- 画面: 旅程の詳細
- 指摘: 予定を表（左に時刻、右に内容）で見せたい（手描き案 1）。「金沢駅 → 兼六園」のように 1つの枠に地点を2つ入れない。代わりに、各地点の滞在時間を「9:00〜10:00」のように示したい
- 判断: 採用
- 対応: U04（#32）。移動は地点の間の行として扱い、地点の行には滞在の開始〜終了を出す。開始・終了の時刻は今のデータ（`start` / `end`）にあるので、表示の変更で対応できる
- 注意: 時刻が分からない予定は時刻を作らず、分からないことを示す（「不明」か「未取得」かは、表記の統一の決定に従う）
- M1 通知: 不要

### R4. 同じ場所でできることを、2つの予定に分けない
- 画面: 候補の比較、旅程の詳細
- 指摘: 同じ場所でまとめてできると思われることを、2つの予定に分けて見せたり計画したりしないでほしい。例: 「寿司店Aで昼食」と「近江町市場で食べ歩き」が重なっている
- 判断: 要調整（計画の作り方の問題）
- 対応: 計画側の D06（#16, M3）旅程の検証と順序調整、A04（#28, M4）旅行計画の実生成。画面は渡された予定を表示するだけなので、M2 だけでは直せない。サンプル（fixture）の見直しは M1・M2
- 調整（契約は変えない）: #16・#28 で、計画の規則（例: 近い場所・近い時間の食事を重ねない）を確認する

### R5. 地図と地点を同期し、地点リストをやめて地図上の点にする
- 画面: 旅程の詳細（今は番号付きの地点リスト）
- 指摘: 地図と地点を同期して表示したい。地点リストはやめ、地図上の点にしたい
- 判断: 採用（地図の表示は、課金とキーの承認の後）。地図は Maps JavaScript SDK（docs/02_ARCHITECTURE.md の `maps` のとおり）
- 対応: U04（#32）。地点の座標は D03（#13, M3）、経路は D04（#14, M3）
- 注意: 地図の帰属表示を残す（U04 の確認項目）
- 調整（契約は変えない）: ブラウザ用のキー（`.env.example` の `PUBLIC_MAPS_BROWSER_KEY`）と Google Cloud の課金は、本人の承認を待つ（CLAUDE.md §2・§7: API 課金を無断で始めない）。キーは HTTP リファラーで制限し、使える API を Maps JavaScript API だけに絞り、1日の上限を付ける。キーは Git に入れない

### R6. 交通手段を日ごとに選べるようにする
- 画面: 条件入力（新規作成）
- 指摘: 交通手段を日ごとに選びたい（例: 11/1 は車、11/2 は公共交通）
- 判断: 要調整（UI 側は対応する方針。契約の変更は M1 の判断待ち）
- 対応: U03（#31）条件入力の実画面
- 理由: 今の `TripConstraints.transportMode`（packages/contracts/src/trip.ts）と K05 の `PlanningContextRequest.transportMode`（packages/contracts/src/planning.ts）は、どちらも旅程全体で1つ。日ごとにするには契約の変更が要り、生成（M4）・経路（M3）にも影響する
- M1 通知（契約）: **要**

### R7. 作った後の旅程で、条件をその場で変えられるようにする
- 画面: 旅程の詳細と編集
- 指摘: 既存の旅程の中で、条件を動的に変えられるようにしたい
- 判断: 要調整（UI 側は対応する方針。契約の変更と再計画の機能は、M1・M4 の判断待ち）
- 対応: U06（#34）＋ A05（#29）代替候補と差分、A06（#30）残り旅程の再計画（M4）
- 理由:
  - K10 の操作は `add`・`remove`・`move`・`update`・`set_title` だけで、条件を変える操作がない。旅程の中で条件を変えるには、K10 に操作を足すか、K01 の `mode=replan` を使うかのどちらかになる
  - K01 の再計画（契約の `mode=replan`、packages/contracts/src/generation.ts）は、今はローカル App Server（apps/ai-local/src/app.ts）が 422 で拒否している。`mode=replan` は A06 まで、`baseTripId`・`expectedRevision` は A04 まで。docs/03_CONTRACTS.md の K01 の節には `mode` の記載がない
  - 前提として、訪問済みの予定と固定の予定は保つ（R12）。変えられる条件の範囲（日程・交通手段・予算など）と、どこまで作り直すかを決める必要がある
- M1 通知（契約）: **要**

## U01 の確認中に見つかった点（参考）
U01 の開発中に、独立したレビュー（reviewer）と文書照合（doc-checker）で見つかった点。人の指摘ではない。U01 のなかで直したものは除く。
- 表記: 同じ画面で「不明」（U01 の部品 `components/labels.ts`）と「未取得」（既存の `TripViewer`、`lib/format.ts`）が混在している。docs/01_SPEC.md は R05 で「不明値は未取得とする」、金額の項で「未取得は null」と定め、R11 は「不明費用」と書く。仕様は値の欠落を「未取得」と表しているので、U01 の「不明」を「未取得」に揃えるかを M2 の表示の判断として決める（調整・契約は変えない）
- 費用不明の件数: 既存の `lib/costs` は徒歩も数えるので、旅程の表示（5件）と変更の差分（4件）が食い違う。main の K10 は徒歩を数えない。U04 で表示を作り直すときに揃える
- 出発帰着（R01）の入力欄がない。U03 で扱う
- `App.tsx` への接続と、DOM のテスト環境（jsdom）の導入は、PR #82 で出した既存の M1 の判断待ち（このレビューの通知とは別）
- docs/03_CONTRACTS.md の K10 の例は、`remove` に `activityId` を使っているが、契約は `itemId`（packages/contracts/src/planning.ts）。U06 の引継ぎで注意する（#83 で M1 に依頼済み）
